\section*{Abstract}
\addcontentsline{toc}{section}{Abstract}

MediTrack is a web-based pharmacy storefront combined with a medicine-inventory
administration console. It supports catalogue browsing with live stock, guest and
signed-in shopping carts, prescription-aware checkout (in progress), sandbox payment,
order fulfilment, role-based back-office operations and an append-only audit trail. The
system is implemented as a three-tier application: a React single-page frontend, a
Node.js/Express REST API and a MongoDB database accessed through Mongoose.

This report documents the project against the MediTrack Software Requirements
Specification v1.0, using the requirements, design, implementation and verification
clauses prescribed by IEEE Std 830-1998, IEEE Std 1016-2009 and IEEE Std 829-2008.
Unlike the earlier draft of this report, which relied on repository documentation
alone, every implementation statement here was checked against the source tree, and
every quantitative statement was produced by executing the artefact on the development
machine.

At the time of writing, the automated backend suite comprises 97 test cases in eight
files, all passing, and the frontend production build completes without warnings.
Verified capabilities include atomic stock reservation with rollback (FR-2.2, NFR-2.1),
server-side pricing computed in paise, a seven-state order lifecycle, card, UPI,
net-banking and cash-on-delivery sandbox payments (FR-2.3), low-stock replenishment at
a configurable water-mark of 10 units up to 100 (FR-1.1), an idempotent MediPoints
ledger credited only after a confirmed payment (FR-2.4), hashed passwords with
short-lived access tokens and rotating refresh sessions (NFR-1.2), permission-based
authorisation on every protected route (NFR-1.1), and an audit log with no update or
delete endpoint (NFR-1.3). Four SRS capabilities remain planned and are specified but
not implemented: cart-level soft holds with automatic release (FR-1.2, FR-1.3), a
wishlist (FR-1.5), prescription upload and verification gating (FR-1.4, FR-2.1) and
refill reminders routed to teleconsultation (FR-2.5). Clause~8.2 gives the
item-by-item assessment and Clause~9.2 the plan for closing them.

\section{Introduction}

\subsection{Purpose}
This report describes the requirements, design, implementation and verification of
MediTrack, a prototype pharmacy storefront. It is intended for the course evaluator,
the project guide and the successor team that will continue development, and it serves
three purposes: to record what the system does and why it is built that way, to
demonstrate traceability from each requirement in the SRS to code and to an executing
test, and to state honestly which requirements are not yet met.

\subsection{Scope}
The reported system covers the customer storefront (catalogue, cart, checkout, payment,
order history, MediPoints; wishlist planned), the Inventory Manager console (stock
administration, order fulfilment, customers, invitations, audit review, manual
replenishment) and the platform services behind them (authentication, sessions,
authorisation, pricing, inventory consistency, payment adapter, audit logging). The SRS
item ``regional demand pattern detection'' is explicitly deferred by the SRS itself and
is out of scope here.

Payment processing is restricted to a deterministic sandbox provider; no real money
moves and no payment credentials are stored. Hardware-dependent barcode/QR and RFID
interactions are simulated or deferred (SRS constraints CON-2 and CON-3).

\section{Overall Description}

\subsection{Product Perspective}
MediTrack is a standalone, three-tier e-commerce system for a single pharmacy. It
replaces a manual counter workflow in which stock levels and sales records are kept
separately. The SRS fixes the architecture: a React client, a Node.js/Express API, a
MongoDB database and a third-party sandbox payment gateway. The prototype is
delivered as an academic system and is not integrated with any existing hospital,
insurance or regulatory system.

Two architectural properties shape the rest of the design. First, the browser is
never trusted with money or stock: prices, availability and totals are recomputed on
the server on every read and write. Second, privileged operations are separated from
customer operations at the API boundary rather than in the user interface, so hiding
a button is never mistaken for a security control.

\subsection{Operating Environment}
The runtime environment fixed by SRS Clause~4.7 and confirmed on the development
machine is Node.js 18 or later (measured: Node.js 22.22.3, npm 10.9.8), MongoDB 6 or
later (local instance or Atlas cluster), a modern browser (Chrome, Firefox, Edge or
Safari) and HTTPS for all client-server traffic in production. The frontend is built
with Vite~5 and can be served from any static host; the SRS names Netlify for the
prototype. Uploaded medicine images are served from the API host under
\texttt{/uploads}.

\subsection{Assumptions and Dependencies}

  \item ASSUME-3: doctors are available for teleconsultation when a refill is due.
  \item The prototype assumes a single pharmacy with one stock pool; batch-level inventory is not modelled (see Clause~8.4).

\end{itemize}

\subsubsection{Information view}
The persistent information view is specified in Clause~6.1 (collections, fields and
indexes) and Clause~6.2 (relationships). The design rule is that each collection owns
exactly one entity, references are stored as ObjectIds with declared indexes, and
commercial values that must not change (unit price, totals, address) are copied into
the order at checkout rather than read through the reference.

Figure~\ref{fig:classmodel} presents the domain class model of the SRS with the
principal attributes and operations of each class. User is specialised into Customer,
Inventory Manager and Auditor; a Customer owns carts, a wishlist, orders, a MediPoints
ledger and prescriptions, and an Order can have several payment attempts. The model is
the design target. In the current build the Auditor is served by the administrator's
audit view (Table~\ref{tab:userclasses}), Payment is embedded in the order, and the
Wishlist, Prescription, RefillReminder and ConsultationBooking classes are planned
(Table~\ref{tab:functions}, Clause~8.2).

\subsubsection{Algorithm view}
Three algorithms carry the correctness of the system. They are written as
single-document conditional updates, because the prototype must also run on a
standalone MongoDB instance without multi-document transactions.

\noindent\textbf{A --- atomic reservation with rollback (FR-1.2, NFR-2.1).} The
condition and the decrement travel in one database operation, so two concurrent
checkouts can never both pass a stock check.
\begin{codeblock}
for each cart line:
    updated = medicine.findOneAndUpdate(
        { _id: id, stock: { $gte: quantity } },      // condition re-evaluated atomically
        { $inc: { stock: -quantity } },
        { new: true })
    if not updated:                                   // someone sold the last unit first
        restore every previously reserved line        // rollback
        throw 409 "...no longer has N unit(s) in stock"

totals  = computeTotals(lines)                        // integer paise, server-side only
order   = insert snapshot + expiry deadline
cart.items = []
\end{codeblock}

\noindent\textbf{B --- watermark replenishment (FR-1.1).} The sweep is idempotent:
after a row is refilled it no longer satisfies the condition, so a second concurrent
sweep matches nothing.
\begin{codeblock}
candidates = medicines.where(stock <= LOW_STOCK_WATERMARK, exp >= today)
for each candidate:
    updated = medicine.findOneAndUpdate(
        { _id: candidate._id, stock: { $lte: LOW_STOCK_WATERMARK } },
        { $set: { stock: REPLENISH_TO } },
        { new: true })
    if not updated: continue                          // another sweep won the race
    audit("medicine.replenish", before={stock}, after={stock})
\end{codeblock}

\noindent\textbf{C --- MediPoints credit (FR-2.4).} Eligibility is decided from the
payment state, and the database enforces ``once per order''.
\begin{codeblock}
if order.payment.status != 'succeeded': return null    // declined, cancelled or COD unpaid
points = floor(subtotal_in_paise / 10000) * MEDIPOINTS_PER_100
try: insert ledgerEntry { user, order, type:'earn', points }
catch duplicate-key on order: return null              // already credited -- harmless replay
\end{codeblock}

\subsubsection{Resource view}
\begin{itemize}[leftmargin=1.2em,itemsep=1pt,topsep=2pt]
  \item \textbf{Process model.} One Node.js process serving HTTP and one unref'd interval timer for replenishment; no worker queue, no external scheduler.
  \item \textbf{Memory.} Bounded by request size (JSON body default limits, 5~MB upload limit) and the in-memory rate-limit store, which grows with the number of distinct IP/e-mail pairs seen inside the window.
  \item \textbf{Storage.} MongoDB holds documents and indexes; uploaded images are files under \texttt{backend/uploads} and are deleted when the medicine is removed or its image replaced.
  \item \textbf{Timers and TTL.} Guest carts carry a TTL index (30 days); orders carry an application-level deadline because stock must be restored, not merely deleted.
  \item \textbf{Scaling limits.} Rate limiting and scheduled sweeps assume a single instance. Multiple instances would need a shared limiter store and an elected sweeper.
\end{itemize}

\subsection{Backend Modules}
The API is composed in \texttt{server.js}, which applies Helmet, credentialed CORS,
JSON parsing and a signed-cookie parser, serves \texttt{/uploads}, mounts the seven
routers, terminates unknown \texttt{/api} paths with 404 and normalises every error
(Mongoose validation, cast and duplicate-key errors, and Multer failures) into
\texttt{\{error\}} with an appropriate status code. Multer's temporary files are removed
when a request fails, so a rejected upload leaves no orphan on disk.

\noindent\textbf{Catalogue and availability.} \texttt{models/Medicine.js} declares name,
manufacturing and expiry dates (stored as \texttt{YYYY-MM-DD} strings), price, integer
stock, an optional image reference, creator, \texttt{prescriptionRequired} and
\texttt{refillDays}. A \texttt{pre('validate')} hook rejects an expiry earlier than the
manufacturing date, so an invalid period cannot be stored even if the client bypasses
the form. \texttt{lib/availability.js} treats a medicine as sellable until the end of
its expiry day and returns a human-readable reason when it is not.

\noindent\textbf{Replenishment.} \texttt{lib/inventory.js} reads its rules from the
environment, refuses an invalid configuration (a refill target at or below the watermark
would refill the same row forever) and exposes \texttt{replenishLowStock()} and
\texttt{startReplenishSweeper()}. The sweep runs once at startup and then on an interval;
the timer is unreferenced so it never keeps a process or a test run alive, and it is
cleared when the server closes. Every refill is audited with the before and after
quantity.

\noindent\textbf{Cart.} \texttt{lib/cartSession.js} resolves the caller's cart from the
JWT or from the signed \texttt{mt\_cart} cookie (path \texttt{/api}, httpOnly,
SameSite=Lax, Secure in production, 30-day lifetime). Only \texttt{sha256(token)} is
stored. \texttt{serializeCart()} re-reads every medicine, so prices, stock and
availability are current; it marks per-line issues and computes totals. Merging a guest
cart into an account cart clamps each line to live stock and to the per-line maximum
instead of failing the sign-in.


\noindent\textbf{Orders and payments.} \texttt{lib/orderService.js} validates the whole
cart before touching stock, reserves line by line, rolls back on failure, snapshots items
and totals, clears the cart and sets the expiry deadline. Order numbers take the form
\texttt{MT-YYYY-XXXXXX} under a unique index with a bounded retry on collision.
\texttt{routes/orders.js} enforces ownership, idempotent payment, expiry checks and
cancellation. \texttt{lib/paymentGateway.js} is a small registry; the mock provider
validates card numbers with the Luhn checksum plus expiry and CVV, accepts UPI with a
valid VPA, accepts five demo banks for net banking and declines cash on delivery above
\rupee5,000.

\noindent\textbf{MediPoints.} \texttt{lib/medipoints.js} computes points from the
subtotal in whole \rupee100 blocks and inserts one ledger entry per order. A unique
partial index on order turns a duplicate credit into a caught duplicate-key error, so a
retried payment cannot earn twice.

\noindent\textbf{Identity and sessions.} \texttt{models/User.js} hashes with bcrypt (ten
rounds) and hides the hash with \texttt{select:false}. \texttt{lib/sessions.js} issues a
32-byte refresh token in a signed httpOnly cookie, stores only its SHA-256 hash with a
device label and expiry, rotates on every refresh, and revokes every session when a
rotated token is replayed outside a short grace window (which covers two tabs refreshing
at once). \texttt{tokenVersion} is embedded in access tokens so a password change or
``sign out everywhere'' invalidates outstanding tokens immediately.

\noindent\textbf{Governance.} \texttt{lib/permissions.js} maps roles to permissions
(\texttt{catalog:read}, \texttt{catalog:write}, \texttt{orders:read:all},
\texttt{orders:write}, \texttt{customers:read}, \texttt{users:manage},
\texttt{invites:manage}, \texttt{audit:read}). \texttt{lib/audit.js} writes a
best-effort entry (actor, actor e-mail, action, target, before/after, IP, user agent) and
never throws. \texttt{middleware/rateLimit.js} limits failed sign-ins per IP and e-mail
and registrations per IP; \texttt{middleware/requestGuards.js} rejects form-encoded
bodies on JSON-only endpoints, closing the cross-site form-post path.

\subsection{Error Conventions}
Every failure returns JSON of the form \texttt{\{ "error": "\ldots" \}}, optionally with
additional context (a declined payment returns \texttt{\{ error, order \}}). Status
codes are used consistently:
\begin{itemize}[leftmargin=1.2em,itemsep=1pt,topsep=2pt]
  \item 400 --- malformed or invalid input (missing field, bad quantity, invalid refill cycle, unsupported payment method).
  \item 401 --- missing, expired or revoked credentials; the SPA responds by refreshing once and retrying.
  \item 402 --- payment declined by the provider; the order stays payable and the reason is stored on it.
  \item 403 --- authenticated but not permitted (customer attempting a staff action, customer on the back-office login).
  \item 404 --- unknown resource, including another user's order, which is deliberately not distinguished from a missing one.
  \item 409 --- state conflict (duplicate e-mail, out of stock, expired reservation, illegal status transition).
  \item 415 --- form-encoded body sent to a JSON-only endpoint.
  \item 429 --- rate limit exceeded, returned as JSON rather than an HTML page.
  \item 500 / 502 --- unexpected server error or provider unavailable; the body never exposes a stack trace.
\end{itemize}

\subsection{Threats to Validity}
\begin{itemize}[leftmargin=1.2em,itemsep=1pt,topsep=2pt]
  \item \textbf{Internal validity.} Tests run against mongodb-memory-server, a real but ephemeral MongoDB. Behaviour that depends on a replica set (multi-document transactions), on network latency between application and database, or on Atlas-specific settings is therefore not exercised.
  \item \textbf{Concurrency realism.} Concurrency is simulated with \texttt{Promise.all} inside one process. This exercises the conditional updates but not true multi-process contention; a load generator would strengthen the claim.
  \item \textbf{External validity.} No load, soak, accessibility or cross-browser testing was performed. The frontend is verified by a successful production build and a manual walkthrough, not by browser automation.
  \item \textbf{Construct validity.} Requirement wording is interpreted, and Table~\ref{tab:interpretation} records every such interpretation so a reviewer can disagree explicitly rather than discover a silent redefinition.
  \item \textbf{Conclusion validity.} A passing suite shows that asserted behaviour holds; it does not prove the absence of defects, and several requirements (FR-1.5, FR-2.1, FR-2.5, NFR-2.2, NFR-2.3) have no automated coverage.
\end{itemize}

\subsection{Discussion of Trade-offs}
\textbf{Correctness without transactions.} The most consequential decision was to make
every stock and status change a single-document conditional update. It keeps the
prototype portable to a standalone MongoDB and gives one clear invariant per operation,
but it moves atomicity for a multi-line checkout into application logic: the code must
remember to compensate earlier lines, and that compensation is exactly what the rollback
branch does. A replica set with a transaction would remove the compensation code at the
cost of a heavier development environment.

\textbf{Where holds belong.} Reserving at checkout (current behaviour) keeps the cart
simple and makes the reservation window coincide with the payment window, when a
customer is most likely to convert. The SRS asks for a hold at add-to-cart, which
protects a customer who is still shopping but needs a second stock counter
(\texttt{held}), a release sweeper and a conversion step at checkout. Phase~C implements
the SRS reading and must keep both counters consistent; that is the highest-risk change
left in the plan and deserves its own suite before any UI work.

\textbf{Replenishment as a background event.} Restocking inside the checkout path would
have simplified the demo but would make a sale mutate stock in two opposite directions
within one request, weakening both the audit story and the reservation arithmetic. A
separate sweep keeps a sale honest and models a supplier delivery, at the cost of stock
remaining at the watermark until the next pass --- visible in the demo by design and
controllable through the manual endpoint.

\textbf{A ledger instead of a counter.} Storing a MediPoints balance on the user would
have been one field and one update. The ledger costs an aggregation per read but buys an
auditable history and a database-enforced ``once per order'' rule that survives a
replayed request --- precisely the failure mode FR-2.4 is about.

\subsection{Limitations}
\begin{itemize}[leftmargin=1.2em,itemsep=1pt,topsep=2pt]
  \item \textbf{Unfinished SRS scope.} Cart soft holds, prescription gating, wishlist, refill reminders and QR/barcode simulation are specified but not built (Tables~\ref{tab:fr} and~\ref{tab:assessment}).
  \item \textbf{No batch-level inventory.} One stock counter and one expiry date per medicine; several batches of the same medicine with different expiry dates cannot be represented. The repository README records the embedded-batch shape to adopt if that becomes a requirement.
  \item \textbf{Single process.} Rate limiting and the replenishment sweep assume one API instance; scaling out needs a shared limiter store and an elected sweeper.
  \item \textbf{Local file storage.} Medicine images live on the API host's disk, so a multi-host deployment needs object storage.
  \item \textbf{No performance evidence.} No load, soak or profiling work was done; this report claims functional correctness, not performance.
  \item \textbf{Limited frontend verification.} Production build plus manual walkthrough; no unit tests, browser automation or accessibility audit for the React code.
  \item \textbf{Prototype operations.} No monitoring, backup or recovery procedure, and TLS termination is delegated to the hosting platform.
\end{itemize}

\section{Conclusion and Future Work}

\subsection{Conclusion}
MediTrack is a working three-tier pharmacy storefront with a back-office console, built
against a formal SRS within the constraints of a one-semester, three-person project. The
parts of the SRS that carry the highest risk --- inventory consistency, payment failure
handling, privilege separation, session security and auditability --- are implemented and
are covered by 97 passing automated tests. The parts that remain are clearly identified
rather than hidden: cart-level soft holds, prescription verification, a wishlist, refill
reminders and QR simulation.

Three outcomes are worth carrying forward. First, the prototype demonstrates that the
important invariants of an e-commerce checkout can be defended without multi-document
transactions, by expressing each one as a conditional single-document update with an
explicit compensation path. Second, the project shows how a requirement can be traced to
a file and to an executing test, which is what makes the status claims in this report
checkable rather than rhetorical. Third, the remaining work is not a research problem
but a sequencing problem: each outstanding requirement has a defined data model,
endpoint and test plan, and the phases are ordered so that each one leaves the system in
a demonstrable state.

\subsection{Future Work}
Remaining work is organised as five increments. Each increment is independently
reviewable, adds its own tests, and updates Appendix~A so the traceability matrix never
lags behind the code.

\subsection*{E.5 Demonstration script}
\begin{enumerate}[leftmargin=1.6em,itemsep=2pt,topsep=2pt]
  \item Sign in at \texttt{/admin/login} as the seeded administrator, then open Stock $\rightarrow$ Add medicine and add a medicine with stock 10, a price of \rupee250, the Rx box ticked and a refill cycle of 21 days.
  \item Wait up to \texttt{REPLENISH\_INTERVAL\_MS} (or press Restock low stock): the quantity moves to 100 and an audit entry \texttt{medicine.replenish} appears under Audit.
  \item Register a customer at \texttt{/login}, add the medicine to the cart and check out. The payment page shows the reservation countdown.
  \item Pay by Net banking $\rightarrow$ HDFC. The order becomes Paid; the receipt shows the MediPoints earned (2 for a \rupee250 subtotal) and the running balance.
  \item Repeat with the demo bank that always declines to show the retry path, and with cash on delivery to show that points are withheld until the money is collected.
\end{enumerate}
