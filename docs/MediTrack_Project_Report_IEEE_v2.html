Abstract

MediTrack is a web-based pharmacy storefront combined with a medicine-inventory administration console. It supports catalogue browsing with live stock, guest and signed-in shopping carts, prescription-aware checkout (in progress), sandbox payment, order fulfilment, role-based back-office operations and an append-only audit trail. The system is implemented as a three-tier application: a React single-page frontend, a Node.js/Express REST API and a MongoDB database accessed through Mongoose.

This report documents the project against the MediTrack Software Requirements Specification v1.0, using the requirements, design, implementation and verification clauses prescribed by IEEE Std 830-1998, IEEE Std 1016-2009 and IEEE Std 829-2008. Unlike the earlier draft of this report, which relied on repository documentation alone, every implementation statement here was checked against the source tree, and every quantitative statement was produced by executing the artefact on the development machine.

At the time of writing, the automated backend suite comprises 148 test cases in eleven files, all passing, and the frontend production build completes without warnings. Verified capabilities include atomic stock reservation with rollback (FR-2.2, NFR-2.1), server-side pricing computed in paise, a seven-state order lifecycle, card, UPI, net-banking and cash-on-delivery sandbox payments (FR-2.3), low-stock replenishment at a configurable water-mark of 10 units up to 100 (FR-1.1), an idempotent MediPoints ledger credited only after a confirmed payment (FR-2.4), hashed passwords with short-lived access tokens and rotating refresh sessions (NFR-1.2), permission-based authorisation on every protected route (NFR-1.1), and an audit log with no update or delete endpoint (NFR-1.3). Four SRS capabilities remain planned and are specified but not implemented: cart-level soft holds with automatic release (FR-1.2, FR-1.3), a wishlist (FR-1.5), prescription upload and verification gating (FR-1.4, FR-2.1) and refill reminders routed to teleconsultation (FR-2.5). Clause 8.2 gives the item-by-item assessment and Clause 9.2 the plan for closing them.

1. Introduction

1.1 Purpose

This report describes the requirements, design, implementation and verification of MediTrack, a prototype pharmacy storefront. It is intended for the course evaluator, the project guide and the successor team that will continue development, and it serves three purposes: to record what the system does and why it is built that way, to demonstrate traceability from each requirement in the SRS to code and to an executing test, and to state honestly which requirements are not yet met.

1.2 Scope

The reported system covers the customer storefront (catalogue, cart, checkout, payment, order history, MediPoints; wishlist planned), the Inventory Manager console (stock administration, order fulfilment, customers, invitations, audit review, manual replenishment) and the platform services behind them (authentication, sessions, authorisation, pricing, inventory consistency, payment adapter, audit logging). The SRS item “regional demand pattern detection” is explicitly deferred by the SRS itself and is out of scope here.

Payment processing is restricted to a deterministic sandbox provider; no real money moves and no payment credentials are stored. Hardware-dependent barcode/QR and RFID interactions are simulated or deferred (SRS constraints CON-2 and CON-3).

2. Overall Description

2.1 Product Perspective

MediTrack is a standalone, three-tier e-commerce system for a single pharmacy. It replaces a manual counter workflow in which stock levels and sales records are kept separately. The SRS fixes the architecture: a React client, a Node.js/Express API, a MongoDB database and a third-party sandbox payment gateway. The prototype is delivered as an academic system and is not integrated with any existing hospital, insurance or regulatory system.

Two architectural properties shape the rest of the design. First, the browser is never trusted with money or stock: prices, availability and totals are recomputed on the server on every read and write. Second, privileged operations are separated from customer operations at the API boundary rather than in the user interface, so hiding a button is never mistaken for a security control.

2.4 Operating Environment

The runtime environment fixed by SRS Clause 4.7 and confirmed on the development machine is Node.js 18 or later (measured: Node.js 22.22.3, npm 10.9.8), MongoDB 6 or later (local instance or Atlas cluster), a modern browser (Chrome, Firefox, Edge or Safari) and HTTPS for all client-server traffic in production. 4.2.9 Algorithm view

Three algorithms carry the correctness of the system. They are written as single-document conditional updates, because the prototype must also run on a standalone MongoDB instance without multi-document transactions.

A — atomic hold, conversion and rollback (FR-1.2, FR-1.3, NFR-2.1). The condition and the counter move travel in one database operation, so two carts can never reserve the same unit and a sale is never counted twice.

// FR-1.2 — taking a hold (lib/cartHolds.js)
held = medicine.findOneAndUpdate(
    { _id: id, stock: { $gte: quantity } },          // stock is what a new customer can buy
    { $inc: { stock: -quantity, held: +quantity } }, // condition re-evaluated atomically
    { new: true })
if not held: throw 409 "…only N unit(s) left in stock"
cart line: quantity, holdExpiresAt = now + CART_HOLD_MINUTES

// FR-1.3 — releasing a lapsed hold (sweeper, cart read, removal, clear, merge)
if cart.findOneAndUpdate(                            // clearing the marker is the claim
      { _id: cartId, items: { $elemMatch: { medicine: id, holdExpiresAt: { $lte: now } } } },
      { $set: { 'items.$[line].holdExpiresAt': null } },
      { arrayFilters: [...] }):
    medicine.updateOne({ _id: id, held: { $gte: quantity } },
                       { $inc: { held: -quantity, stock: +quantity } })

// checkout — the hold becomes the sale
sold = medicine.findOneAndUpdate({ _id: id, held: { $gte: quantity } },
                                 { $inc: { held: -quantity } })
if not sold:                                          // hold lapsed or was spent
    reserve from stock instead (conditional decrement)
if any line fails:
    undo every earlier line: restoreHold() puts units back into held,
    a stock reservation is incremented back onto the shelf

totals  = computeTotals(lines)                        // integer paise, server-side only
order   = insert snapshot + expiry deadline
cart.items = []

B — watermark replenishment (FR-1.1). The sweep is idempotent: after a row is refilled it no longer satisfies the condition, so a second concurrent sweep matches nothing.

candidates = medicines.where(stock <= LOW_STOCK_WATERMARK, exp >= today)
for each candidate:
    updated = medicine.findOneAndUpdate(
        { _id: candidate._id, stock: { $lte: LOW_STOCK_WATERMARK } },
        { $set: { stock: REPLENISH_TO } },
        { new: true })
    if not updated: continue                          // another sweep won the race
    audit("medicine.replenish", before={stock}, after={stock})

C — MediPoints credit (FR-2.4). Eligibility is decided from the payment state, and the database enforces “once per order”.

if order.payment.status != 'succeeded': return null    // declined, cancelled or COD unpaid
points = floor(subtotal_in_paise / 10000) * MEDIPOINTS_PER_100
try: insert ledgerEntry { user, order, type:'earn', points }
catch duplicate-key on order: return null              // already credited — harmless replay

4.2.10 Resource view

  • Process model. One Node.js process serving HTTP and one unref'd interval timer for replenishment; no worker queue, no external scheduler.
  • Memory. Bounded by request size (JSON body default limits, 5 MB upload limit) and the in-memory rate-limit store, which grows with the number of distinct IP/e-mail pairs seen inside the window.
  • Storage. MongoDB holds documents and indexes; uploaded images are files under backend/uploads and are deleted when the medicine is removed or its image replaced.
  • Timers and TTL. Guest carts carry a TTL index (30 days); orders carry an application-level deadline because stock must be restored, not merely deleted.
  • Scaling limits. Rate limiting and scheduled sweeps assume a single instance. Multiple instances would need a shared limiter store and an elected sweeper.

5.3 Backend Modules

The API is composed in server.js, which applies Helmet, credentialed CORS, JSON parsing and a signed-cookie parser, serves /uploads, mounts the seven routers, terminates unknown /api paths with 404 and normalises every error (Mongoose validation, cast and duplicate-key errors, and Multer failures) into { error } with an appropriate status code. Multer's temporary files are removed when a request fails, so a rejected upload leaves no orphan on disk.

Catalogue and availability. models/Medicine.js declares name, manufacturing and expiry dates (stored as YYYY-MM-DD strings), price, integer stock, an optional image reference, creator, prescriptionRequired and refillDays. A pre('validate') hook rejects an expiry earlier than the manufacturing date, so an invalid period cannot be stored even if the client bypasses the form. lib/availability.js treats a medicine as sellable until the end of its expiry day and returns a human-readable reason when it is not.

Replenishment. lib/inventory.js reads its rules from the environment, refuses an invalid configuration (a refill target at or below the watermark would refill the same row forever) and exposes replenishLowStock() and startReplenishSweeper(). The sweep runs once at startup and then on an interval; the timer is unreferenced so it never keeps a process or a test run alive, and it is cleared when the server closes. Every refill is audited with the before and after quantity.

Cart. lib/cartSession.js resolves the caller's cart from the JWT or from the signed mt_cart cookie (path /api, httpOnly, SameSite=Lax, Secure in production, 30-day lifetime). Only sha256(token) is stored. serializeCart() re-reads every medicine, so prices, stock and availability are current; it marks per-line issues and computes totals. Merging a guest cart into an account cart clamps each line to live stock and to the per-line maximum instead of failing the sign-in.

Orders and payments. lib/orderService.js validates the whole cart before touching stock, reserves line by line, rolls back on failure, snapshots items and totals, clears the cart and sets the expiry deadline. Order numbers take the form MT-YYYY-XXXXXX under a unique index with a bounded retry on collision. routes/orders.js enforces ownership, idempotent payment, expiry checks and cancellation. lib/paymentGateway.js is a small registry; the mock provider validates card numbers with the Luhn checksum plus expiry and CVV, accepts UPI with a valid VPA, accepts five demo banks for net banking and declines cash on delivery above ₹5,000.

MediPoints. lib/medipoints.js computes points from the subtotal in whole ₹100 blocks and inserts one ledger entry per order. A unique partial index on order turns a duplicate credit into a caught duplicate-key error, so a retried payment cannot earn twice.

Identity and sessions. models/User.js hashes with bcrypt (ten rounds) and hides the hash with select:false. lib/sessions.js issues a 32-byte refresh token in a signed httpOnly cookie, stores only its SHA-256 hash with a device label and expiry, rotates on every refresh, and revokes every session when a rotated token is replayed outside a short grace window (which covers two tabs refreshing at once). tokenVersion is embedded in access tokens so a password change or “sign out everywhere” invalidates outstanding tokens immediately.

Governance. lib/permissions.js maps roles to permissions (catalog:read, catalog:write, orders:read:all, orders:write, customers:read, users:manage, invites:manage, audit:read). lib/audit.js writes a best-effort entry (actor, actor e-mail, action, target, before/after, IP, user agent) and never throws. middleware/rateLimit.js limits failed sign-ins per IP and e-mail and registrations per IP; middleware/requestGuards.js rejects form-encoded bodies on JSON-only endpoints, closing the cross-site form-post path.

6.4 Error Conventions

Every failure returns JSON of the form { "error": "…" }, optionally with additional context (a declined payment returns { error, order }). Status codes are used consistently:

  • 400 — malformed or invalid input (missing field, bad quantity, invalid refill cycle, unsupported payment method).
  • 401 — missing, expired or revoked credentials; the SPA responds by refreshing once and retrying.
  • 402 — payment declined by the provider; the order stays payable and the reason is stored on it.
  • 403 — authenticated but not permitted (customer attempting a staff action, customer on the back-office login).
  • 404 — unknown resource, including another user's order, which is deliberately not distinguished from a missing one.
  • 409 — state conflict (duplicate e-mail, out of stock, expired reservation, illegal status transition).
  • 415 — form-encoded body sent to a JSON-only endpoint.
  • 429 — rate limit exceeded, returned as JSON rather than an HTML page.
  • 500 / 502 — unexpected server error or provider unavailable; the body never exposes a stack trace.

7.8 Threats to Validity

  • Internal validity. Tests run against mongodb-memory-server, a real but ephemeral MongoDB. Behaviour that depends on a replica set (multi-document transactions), on network latency between application and database, or on Atlas-specific settings is therefore not exercised.
  • Concurrency realism. Concurrency is simulated with Promise.all inside one process. This exercises the conditional updates but not true multi-process contention; a load generator would strengthen the claim.
  • External validity. No load, soak, accessibility or cross-browser testing was performed. The frontend is verified by a successful production build and a manual walkthrough, not by browser automation.
  • Construct validity. Requirement wording is interpreted, and Table 8 records every such interpretation so a reviewer can disagree explicitly rather than discover a silent redefinition.
  • Conclusion validity. A passing suite shows that asserted behaviour holds; it does not prove the absence of defects, and several requirements (FR-2.1, FR-2.5, NFR-2.2, NFR-2.3) have no automated coverage.

8.3 Discussion of Trade-offs

Correctness without transactions. The most consequential decision was to make every stock and status change a single-document conditional update. It keeps the prototype portable to a standalone MongoDB and gives one clear invariant per operation, but it moves atomicity for a multi-line checkout into application logic: the code must remember to compensate earlier lines, and that compensation is exactly what the rollback branch does. A replica set with a transaction would remove the compensation code at the cost of a heavier development environment.

Where holds belong. Reserving at checkout keeps the cart simple and makes the reservation window coincide with the payment window, when a customer is most likely to convert. The SRS asks for a hold at add-to-cart, which protects a customer who is still shopping, at the cost of a second stock counter (held), a release sweeper and a conversion step at checkout. Phase C implements the SRS reading: stock is what a new customer can buy, held is what live carts are promised, and stock + held is the physical quantity, which only a completed sale or a replenishment changes. Both counters move in single conditional updates (acquireHold, releaseHold, convertHoldToSale, restoreHold) and the invariant is asserted by its own suite before any UI work.

Replenishment as a background event. Restocking inside the checkout path would have simplified the demo but would make a sale mutate stock in two opposite directions within one request, weakening both the audit story and the reservation arithmetic. A separate sweep keeps a sale honest and models a supplier delivery, at the cost of stock remaining at the watermark until the next pass — visible in the demo by design and controllable through the manual endpoint.

A ledger instead of a counter. Storing a MediPoints balance on the user would have been one field and one update. The ledger costs an aggregation per read but buys an auditable history and a database-enforced “once per order” rule that survives a replayed request — precisely the failure mode FR-2.4 is about.

8.4 Limitations

  • Unfinished SRS scope. Cart soft holds, prescription gating, wishlist, refill reminders and QR/barcode simulation are specified but not built (Tables 6 and 30).
  • No batch-level inventory. One stock counter and one expiry date per medicine; several batches of the same medicine with different expiry dates cannot be represented. The repository README records the embedded-batch shape to adopt if that becomes a requirement.
  • Single process. Rate limiting and the replenishment sweep assume one API instance; scaling out needs a shared limiter store and an elected sweeper.
  • Local file storage. Medicine images live on the API host's disk, so a multi-host deployment needs object storage.
  • No performance evidence. No load, soak or profiling work was done; this report claims functional correctness, not performance.
  • Limited frontend verification. Production build plus manual walkthrough; no unit tests, browser automation or accessibility audit for the React code.
  • Prototype operations. No monitoring, backup or recovery procedure, and TLS termination is delegated to the hosting platform.

9. Conclusion and Future Work

9.1 Conclusion

MediTrack is a working three-tier pharmacy storefront with a back-office console, built against a formal SRS within the constraints of a one-semester, three-person project. The parts of the SRS that carry the highest risk — inventory consistency, payment failure handling, privilege separation, session security and auditability — are implemented and are covered by 148 passing automated tests. The parts that remain are clearly identified rather than hidden: prescription verification, refill reminders and QR/barcode simulation, plus the hardening work of Phase F.

Three outcomes are worth carrying forward. First, the prototype demonstrates that the important invariants of an e-commerce checkout can be defended without multi-document transactions, by expressing each one as a conditional single-document update with an explicit compensation path. Second, the project shows how a requirement can be traced to a file and to an executing test, which is what makes the status claims in this report checkable rather than rhetorical. Third, the remaining work is not a research problem but a sequencing problem: each outstanding requirement has a defined data model, endpoint and test plan, and the phases are ordered so that each one leaves the system in a demonstrable state.

9.2 Future Work

Phases A, B and C are delivered, each with its own test suite and an updated Appendix A. Remaining work is organised as three increments. Each increment is independently reviewable, adds its own tests, and updates Appendix A so the traceability matrix never lags behind the code.

E.5 Demonstration script

  1. Sign in at /admin/login as the seeded administrator, then open Stock → + Add medicine and add a medicine with stock 10, a price of ₹250, the Rx box ticked and a refill cycle of 21 days.
  2. Wait up to REPLENISH_INTERVAL_MS (or press Restock low stock): the quantity moves to 100 and an audit entry medicine.replenish appears under Audit.
  3. Register a customer at /login, add the medicine to the cart and check out. The payment page shows the reservation countdown.
  4. Pay by Net banking → HDFC. The order becomes Paid; the receipt shows the MediPoints earned (2 for a ₹250 subtotal) and the running balance.
  5. Repeat with the demo bank that always declines to show the retry path, and with cash on delivery to show that points are withheld until the money is collected.
